# 第三層 Work Log 與方法規格

## Work Log 日期段落

每天只保留一個 `## YYYY-MM-DD`，最新日期在前。同一天再次記錄時合併內容、移除重複，不覆蓋已成立的研究脈絡。沒有內容的三級標題可省略。

```markdown
## 2026-09-23

### 今日工作

- **研究問題／假設**：描述今天真正處理的研究問題與採用方法。

### 結果與驗證

- **研究結論**：交代比較基準、期間、口徑與結果解讀。

### 決策與待處理

- ==待確認決策 D1：是否採用新的訊號定義？==
- ==重要限制：目前資料尚未涵蓋完整景氣循環。==
```

記錄脈絡採 `研究問題 → 假設 → 方法／規則 → 結果 → 解讀`，不按修改檔案或工作時間流水排列。

## 內容取捨

- 保存會影響最終方法、結果解讀或未來重現的失敗與取捨；不複製終端輸出或普通除錯過程。
- Notebook、圖表與輸出物以穩定 Markdown／Obsidian 連結指向，不把大量數據整份複製到 Log。
- 重要量化結果必須交代研究問題、比較基準、期間與口徑；不只保留最好看的績效數字。
- 程式碼改動只有在改變訊號、資料口徑、回測、權重、交易規則或結果解讀時才進入主文。
- 測試與重構只作必要佐證，不以測試數量或 `Unit-tested` 作為研究成果標題。

## 視覺強調

- `**粗體**`：研究假設、訊號邏輯、資料定義、策略規則與有意義的結果。
- `==反白==`：需要使用者注意或確認的決策、風險、阻塞與重要結論。
- 每個日期最多三個反白項目；粗體與反白不可重疊。

## 方法／規格更新

只有經使用者明確確認、而且會持續沿用的資料口徑、PIT 契約、訊號、模型、回測、權重、交易規則或正式作業流程才能更新規格。

- 程式已實作不等於正式採用。
- 更新既有主規格或對應子規格，不建立重複 README。
- 規格只保留目前有效方法；舊方法與改變原因留在 Work Log，並由 Log 連到更新後的規格段落。
- 規格以粗體標示正式規則，以反白標示適用範圍、重要限制與禁止事項；正式規格不得含待確認決策。

## 研究／實作交接

沿用三個既有日誌區段，以粗體前綴補上有內容的研究、實作或交接事項：

- 今日工作：原型依據的是哪個正式規格或暫定假設。
- 結果與驗證：預期行為、實際結果、重要差異及可重現依據；不能重跑的資料或環境限制需說明。
- 決策與待處理：下一端可接續的工作、相關分支／檔案／已存在 commit 與尚待確認的問題。

未確認方案可在使用者確認寫入後保存於日誌的待確認區，不必為了保存交接而強迫先做研究決策。不得將其寫入正式規格。當次提交的 commit hash 在提交成功後回報，不為了將 commit 寫入它自己的內容反覆 amend。

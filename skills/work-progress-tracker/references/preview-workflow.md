# 決策確認與寫入預覽

## 「紀錄今天進度」不是寫入指令

收到「紀錄今天進度」、收工或更新紀錄要求時，先蒐集證據並形成草稿，不修改任何來源 Markdown，也不發布 K 槽。

## 階段一：候選重大決策

將可能改變資料契約、訊號、模型、回測、權重、交易規則、專案範圍或正式交付的候選決策逐項編號：

```markdown
### 待確認重大決策

- **D1**：候選決策內容
  - 原因：為什麼形成這個選項
  - 影響：會改變哪些研究或文件
  - 請回覆：確認／否決／修改
```

未確認項目在預覽中列入 Work Log 待確認區，使用者確認寫入後可保存，以便跨裝置接續。不得寫入正式規格、Progress 的已確認決策或 PROJECTS 的決策／結論。Progress 可記錄「口徑待確認」等客觀狀態並連到 Log。

## 階段二：依變更選擇預覽

一般工作紀錄使用精簡預覽：只展示第三層新增／合併內容、Progress 改動、PROJECTS 入選項目，以及提交與發布範圍；不重貼整份既有文件。精簡的是展示長度，不是隱藏修改。

重大決策或方法／規格變更提供以下完整預覽，另交代改變原因、影響與驗收方式：

決策處理完後，依序顯示：

1. `Work Log 擬新增／合併內容`
2. `研究方法／規格擬修改內容`；沒有改變時明寫「本次不更新研究方法／規格」
3. `PROGRESS 擬更新內容`：摘要、流程表或目前狀態的變化，以及依五種可選分類整理的當日 Callout
4. `PROJECTS 預計呈現`：管理狀態／研究階段、里程碑、最新重點、目前狀態與分類後的最近重要更新
5. `預計修改與發布的檔案`：分列 GitHub 與 K 槽；GitHub 包含 repo、remote、工作分支、明確檔案及變更摘要、既有未推送提交。K 槽只發布 allowlist 文件。

預覽使用可閱讀的 Markdown 草稿，不要求使用者閱讀原始 diff。此時仍不寫檔。

## 寫入授權

- 使用者在看到目前有效預覽後回覆「確認寫入」，即授權依預覽更新文件、commit、push 工作分支與發布 K 槽，不再逐步詢問。使用者明確指定其他授權表達時依當次指示。
- 「OK」「看起來可以」「紀錄今天進度」等一般肯定不視為寫入授權。
- 使用者可逐項修改或否決；修改後重新顯示受影響的預覽。
- 等待期間若來源 Markdown、notebook 結果、artifacts、提交清單或遠端基準改變，重新檢查並更新受影響預覽。重大決策已明確確認且內容未變時，不重複詢問。
- 沒有實質研究進度時，不建立空白日期或 Callout；仍可針對待同步的相關成果預覽提交範圍。

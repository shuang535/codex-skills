# 三層文件模型

## 閱讀與提煉方向

```text
第三層：Work Log／研究方法與規格
  ↓ 提煉研究意義
第二層：PROGRESS 專案作業中心
  ↓ 提煉管理重點
第一層：PROJECTS 跨專案入口
```

第一層只讀第二層；第二層以第三層與實際 artifacts 為依據。K 槽是發布位置，不是第四層。

## 文件責任

| 層級／角色 | 保存內容 | 不保存內容 | 更新時機 |
|---|---|---|---|
| `PROJECTS.md` | 管理狀態、研究階段、里程碑、最新重點、分類後的最近重要更新與入口 | 每日實驗、一般程式實作 | 每次成功發布時由程式重建 |
| `PROGRESS.md` | 專案定位、流程與規劃、目前狀態、每日研究摘要、已確認決策 | 完整研究過程、未確認決策 | 有實質進度且使用者確認寫入 |
| Work Log | 研究問題、假設、方法、結果、解讀、重要失敗、取捨、阻塞與待處理事項 | 假裝成正式方法的候選方案 | 每次經確認的進度寫入 |
| Main／Sub specification | 目前正式採用的方法、資料契約、模型、回測、權重、交易與治理規則 | 每日過程、未確認方案、舊版實驗細節 | 使用者確認持久方法改變時 |
| Delivery notes | 特定交付物的敘事、版本與限制 | 專案現行方法的唯一真相 | 正式交付改變時 |

沿用專案既有 source-of-truth map，不為了套模板建立第二套文件。若缺少 Work Log 或規格，先提出檔名與內容預覽，經「確認寫入」後才建立。

## 研究與實作交接

- 第三層保存暫定方案、原型驗證、實作差異與接手依據；方法規格只保存已確認方法。待確認問題可經寫入確認後保存於 Work Log，不能冒充正式決策。
- 第二層在既有目前狀態及每日分類中使用「研究／實作／交接」前綴，記錄目前分工狀態、驗收依據與第三層入口。只填有內容項目，不另增一層或固定必填表。
- 第一層只取第二層已選取的管理重點；技術交接步驟、分支操作與細部 Todo 留在第三層。
- GitHub 保存可接續版本，K 槽是可補發布的閱讀中心；repo 文件使用相對入口，不依賴本機絕對路徑。

## 研究成熟度

第二層使用研究語言，而非軟體測試語言：

```text
假設形成 → 資料確認 → 策略建構 → 回測驗證
→ 穩健性檢查 → 正式交付 → 持續監控
```

管理狀態仍只用：`進行中`、`待驗證`、`待審核`、`已交付`、`暫停`。管理狀態和研究成熟度是兩個欄位，不互相代替。

Tests、重構、函式數量或 `Unit-tested` 不是研究進度主角。只有它們改變研究邏輯、結果可信度或重現性時，才以研究意義描述，例如「重跑確認新邏輯不改變既有訊號」，而不是突出測試數量。

## 向上提煉標準

只有下列資訊能從 Work Log 進入 Progress：

- 改變專案階段或里程碑。
- 改變研究假設、資料定義、訊號、策略規則或結果解讀。
- 形成可比較的研究結論或正式交付。
- 經使用者確認的持久方法決策。

只有改變專案方向、正式方法或交付的已確認決策，才繼續進入 PROJECTS。進入第一層的內容依 `進度與成果`、`方法／規格變更`、`已確認重大決策`、`交付物`、`風險／限制` 分類，同一事項只出現一次；一般研究取捨留在 Progress，完整過程留在 Work Log。

# 第二層 Progress 文件格式

每個 registry 專案必須有且只有一份 `role=progress` 文件。它是專案作業中心，也是第一層 Dashboard 的唯一專案內容來源。

## 固定區段

下列四個二級標題各只能出現一次：

```markdown
## 專案摘要

- **專案定位**：專案長期目的，80 字以內。
- **管理狀態**：進行中
- **研究階段**：策略建構
- **目前里程碑**：目前要完成的階段成果，40 字以內。
- **最新摘要**：目前最重要的進度、成果、決策、交付或風險，80 字以內。
- **最後更新**：2026-09-23

## 作業流程與規劃

| 階段 | 目標產出 | 狀態 | 相依關係 |
|---|---|---|---|
| 資料定義 | 確認資料口徑 | 進行中 | 無 |
| 訊號研究 | 建立候選訊號 | 尚未開始 | 資料定義 |

## 目前狀態

- 最多三點，只保留現在仍成立的狀態。

## 每日進度

### 2026-09-23

> [!summary]+ 2026-09-23
>
> **進度與成果**
>
> - **資料**：完成研究資料範圍確認。
> - **策略**：完成主要方案比較，方案 A 表現較穩定。
>
> **方法／規格變更**
>
> - 正式資料截止日改採月末可得資料。
>
> **已確認重大決策**
>
> - ==正式版本採用方案 A。==
>
> **交付物**
>
> - 完成研究報告與三張簡報圖表。
>
> **風險／限制**
>
> - ==目前資料尚未涵蓋完整景氣循環。==
>
> **詳細紀錄**
>
> - [[WORKLOG#2026-09-23|當日 Work Log]]
```

每日只顯示有內容的分類，但至少要有一項實質內容。日期 heading 提供穩定 Obsidian 錨點。

## 每日分類

分類固定依下列順序排列：

1. `進度與成果`：完成事項、研究發現與有意義的量化結果。
2. `方法／規格變更`：資料口徑、訊號、模型、回測、權重或正式流程改變。
3. `已確認重大決策`：已取得使用者確認，且影響方向、方法或交付的決策。
4. `交付物`：報告、名單、圖表或正式輸出。
5. `風險／限制`：會影響研究解讀、可信度或交付的重大問題。

- 分類內不設固定點數上限；每一點仍須符合向上提煉標準。
- 同一事項只放在一個主要分類，不在同一日期的不同分類重複。
- 同類內容較多時，可用 `**資料**`、`**策略**`、`**視覺化**` 等粗體前綴分群，不再建立巢狀標題。
- 不接受自訂分類名稱；未知分類視為格式錯誤。
- `詳細紀錄` 不屬於管理分類，只保存穩定的第三層文件連結。

## 欄位規則

- 管理狀態只用：`進行中`、`待驗證`、`待審核`、`已交付`、`暫停`。
- 研究階段只用：`假設形成`、`資料確認`、`策略建構`、`回測驗證`、`穩健性檢查`、`正式交付`、`持續監控`。
- 作業流程表只有跨階段、里程碑或相依關係改變時才更新；細部 Todo 留在 Work Log。
- 每次新增每日 Callout，也要更新專案摘要與目前狀態，移除或改寫已過期內容。
- 最新日期使用 `[!summary]+` 展開；所有歷史日期使用 `[!summary]-` 收合。
- 日期採 Asia/Taipei `YYYY-MM-DD`、最新在前；最後更新必須等於最新 Callout 日期。
- 同一天只保留一個 Callout，再次記錄時合併，不建立重複日期。
- 每點採單行、一至兩句；完整研究過程只放第三層 Work Log。
- 待確認方案的詳細內容留在 Work Log；Progress 只記錄客觀的等待狀態與 Log 入口，不把候選方案列為已確認決策。已成立且影響專案階段、研究邏輯、策略結果或正式方法的內容才向上提煉。
- 粗體標示主題、目前階段與研究結論；反白只標示已確認重大決策、重大風險或關鍵結論。
- 沒有實質研究進度時不建立日期或 Callout。

## PROJECTS 向上提煉

PROJECTS 只選取 Progress 中值得跨專案管理閱讀的內容，不原封不動複製每日 Callout。

- 摘要表「最新重點」直接使用 `最新摘要`，不由產生器猜測或拼接。
- 專案區塊保留最多三點目前狀態與最近兩個重要更新日。
- 每日分類沿用 Progress 的五種分類與固定順序，只顯示非空分類。
- 一般程式修改、測試數量與除錯過程不進入 PROJECTS。

### 明確選取標記

在「每日進度」標題下加入獨立一行 `<!-- dashboard:explicit -->`，每個要進入 PROJECTS 的分類項目末尾加 `<!-- dashboard:include -->`。由 agent 在預覽中提出入選項目，使用者可調整，不要求使用者手工標記。

```markdown
## 每日進度

<!-- dashboard:explicit -->

### 2026-10-19

> [!summary]+ 2026-10-19
>
> **進度與成果**
>
> - **研究**：完成候選方案比較。 <!-- dashboard:include -->
> - **實作**：完成中間資料檢查，詳見工作日誌。
```

- 明確模式只帶入標記項目，去除標記後呈現，保留五種分類與原順序；分類內不設點數上限。
- 遍歷全部日期，取最近兩個有入選內容的日期，不先截取最近兩天。沒有今日重點則保留歷史重點並顯示重點日期。
- 完全沒有入選內容時，recent_updates 為空，仍顯示摘要、目前狀態與文件入口，不退回全部複製。
- 即使漏掉模式宣告，只要分類項目中有 include 標記，也採明確模式。宣告仍應保留，確保刪掉最後一個標記後不會回到舊模式。
- 最後更新仍等於最新 Progress Callout 日期；可能晚於最近入選重點日期，兩者不可混用。
- 目前狀態維持最多三點；可用研究／實作／交接前綴呈現。待確認問題只寫客觀等待狀態及 Log 入口，不能當作已採用方案。

## 舊版相容與遷移

產生器仍可唯讀解析兩種舊格式：

- 舊版 Callout 的 `重點進度` 與 `研究結論／成果` 合併為 `進度與成果`，`已確認決策` 對應 `已確認重大決策`。
- 更舊版的 `狀態／證據／摘要／最後更新` 與 `重大進度歷史` 繼續支援；沒有研究階段時顯示 `未標示`。

某專案下一次經「確認寫入」更新時，先在預覽中提出完整新版 Progress，再經使用者確認後遷移；不得只改一半而留下混合格式。

未含模式宣告及 include 標記的既有文件沿用舊模式（最近兩日全部分類），避免讀取即改變既有入口。遷移時加入明確模式，預覽選取最近需要保留的歷史重點；不為啟用新 skill 批次改寫其他專案。已使用新版 Callout 格式者只需補宣告與選取標記，不重寫既有歷史。
